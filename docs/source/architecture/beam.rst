The BEAM Package
================

The ``openstef_beam`` package implements the **Backtesting, Evaluation, Analysis, and Metrics** framework for OpenSTEF. Where the core and models packages handle data structures and forecasting algorithms, BEAM answers the harder question: *how well does a model actually perform under realistic conditions?* This page covers the four phases of the BEAM workflow, the interfaces that connect them, and how to assemble complete evaluation pipelines using the library.

.. note::

   BEAM depends on both ``openstef_core`` (for ``TimeSeriesDataset`` and ``VersionedTimeSeriesDataset``) and ``openstef_models`` (for trained forecasters). See the :doc:`core` and :doc:`models` pages for details on those packages.

Why Realistic Evaluation Matters
---------------------------------

Simple train/test splits are not sufficient for energy forecasting. A model evaluated on a static held-out window may look excellent while silently exploiting future information — a problem called *data leakage*. BEAM prevents this by replaying history through a ``VersionedTimeSeriesDataset``: at every simulated prediction moment the model can only see data that would have been available in production at that exact time. Retraining is triggered on the same schedule it would follow in deployment, and predictions are stamped with an ``available_at`` timestamp so downstream evaluation can filter by lead time.

The result is an evaluation that mirrors what the model would actually deliver in an operational setting.


Phase 1 — Backtesting
----------------------

The backtesting phase is the engine of BEAM. ``BacktestPipeline`` drives a chronological simulation over a historical window, alternating between ``train`` and ``predict`` events generated by ``BacktestEventGenerator``. At each prediction step the forecaster receives a ``RestrictedHorizonVersionedTimeSeries`` — a view of the dataset that enforces the no-lookahead constraint.

Any forecaster that implements ``BacktestForecasterMixin`` can be plugged in. The interface is intentionally minimal:

.. code-block:: python

   from datetime import timedelta
   from openstef_beam.backtesting.backtest_forecaster.mixins import (
       BacktestForecasterMixin,
       BacktestForecasterConfig,
   )
   from openstef_beam.backtesting.restricted_horizon_timeseries import (
       RestrictedHorizonVersionedTimeSeries,
   )
   from openstef_core.datasets import TimeSeriesDataset
   from openstef_core.types import Quantile

   class MedianBaseline(BacktestForecasterMixin):
       """Predicts the rolling median of recent load as a simple baseline."""

       config = BacktestForecasterConfig(
           requires_training=True,
           predict_sample_interval=timedelta(minutes=15),
           predict_length=timedelta(hours=48),
           predict_min_length=timedelta(hours=1),
           predict_context_length=timedelta(days=14),
           predict_context_min_coverage=0.5,
           training_context_length=timedelta(days=90),
           training_context_min_coverage=0.5,
       )

       @property
       def quantiles(self) -> list[Quantile]:
           return [Quantile(0.05), Quantile(0.50), Quantile(0.95)]

       def fit(self, data: RestrictedHorizonVersionedTimeSeries) -> None:
           window = data.get_window(
               data.horizon - self.config.training_context_length,
               data.horizon,
               available_before=data.horizon,
           )
           self._median = float(window["load"].median())

       def predict(
           self, data: RestrictedHorizonVersionedTimeSeries
       ) -> TimeSeriesDataset | None:
           import pandas as pd
           idx = pd.date_range(
               data.horizon,
               periods=int(self.config.predict_length / self.config.predict_sample_interval),
               freq=self.config.predict_sample_interval,
           )
           return TimeSeriesDataset(
               pd.DataFrame(
                   {
                       "quantile_P05": self._median,
                       "quantile_P50": self._median,
                       "quantile_P95": self._median,
                   },
                   index=idx,
               )
           )

``BacktestForecasterConfig`` controls the temporal geometry of the simulation: how far ahead the model predicts, how much context it receives, and how often it is retrained. The ``prediction_sample_interval`` declared in ``BacktestConfig`` must match the forecaster's own ``predict_sample_interval`` — BEAM raises a ``ValueError`` at construction time if they disagree, catching misconfiguration early.

For models that can amortise inference across multiple horizons, ``BacktestBatchForecasterMixin`` extends the interface with a ``predict_batch`` method, enabling significant throughput improvements when running large-scale benchmarks.

Running the pipeline directly is straightforward when you already have versioned datasets:

.. code-block:: python

   from datetime import datetime
   from openstef_beam.backtesting.backtest_pipeline import BacktestPipeline, BacktestConfig

   config = BacktestConfig(prediction_sample_interval=timedelta(minutes=15))
   pipeline = BacktestPipeline(config=config, forecaster=MedianBaseline())

   predictions = pipeline.run(
       ground_truth=versioned_ground_truth,
       predictors=versioned_predictors,
       start=datetime(2023, 1, 1),
       end=datetime(2023, 12, 31),
       show_progress=True,
   )

The return value is a ``TimeSeriesDataset`` containing every prediction made during the simulation, each row tagged with the ``available_at`` timestamp that enables lead-time-aware evaluation downstream.


Phase 2 — Evaluation
---------------------

Once backtesting produces a prediction dataset, the evaluation phase scores it against ground truth. ``EvaluationConfig`` specifies which time windows to evaluate and which metric providers to apply. Windows can represent operational periods such as day-ahead (D-1) or intraday horizons, making it straightforward to report performance at the lead times that matter for a given use case.

BEAM ships several built-in metric providers:

- ``RMAEProvider`` — relative Mean Absolute Error, normalised per target
- ``RCRPSProvider`` — relative Continuous Ranked Probability Score, measuring probabilistic sharpness
- ``RCRPSSampleWeightedProvider`` — sample-weighted variant of rCRPS
- ``PeakMetricProvider`` — precision/recall metrics focused on peak load events

Custom metrics are supported by implementing the ``MetricProvider`` interface, so domain-specific scoring criteria can be added without modifying library code.

.. code-block:: python

   from openstef_beam.evaluation import EvaluationConfig, Window
   from openstef_beam.evaluation.metric_providers import RMAEProvider, RCRPSProvider

   eval_config = EvaluationConfig(
       windows=[
           Window(name="day_ahead", min_lead=timedelta(hours=12), max_lead=timedelta(hours=36)),
           Window(name="intraday", min_lead=timedelta(hours=1), max_lead=timedelta(hours=6)),
       ],
       metric_providers=[RMAEProvider(), RCRPSProvider()],
   )


Phase 3 — Analysis
------------------

The analysis phase transforms raw evaluation scores into human-readable reports and interactive visualisations. BEAM provides a set of built-in visualisation types that cover the most common reporting needs:

- ``GroupedTargetMetricVisualization`` — bar charts comparing metric values across target groups
- ``SummaryTableVisualization`` — tabular overview of all metrics across all targets
- ``PrecisionRecallCurveVisualization`` — precision/recall curves for peak detection, with an ``effective_precision_recall`` variant
- ``QuantileProbabilityVisualization`` — calibration plots checking whether predicted quantiles match empirical frequencies
- ``TimeSeriesVisualization`` — overlaid plots of predictions versus actuals for individual targets

All visualisations are rendered as self-contained HTML files, making them easy to share without additional infrastructure.


Phase 4 — Benchmarking
-----------------------

The benchmarking layer orchestrates the three phases above across many targets and multiple model configurations. ``BenchmarkPipeline`` accepts a ``SimpleTargetProvider`` (or a custom subclass), a set of forecaster factories, and storage configuration, then runs the full Backtesting → Evaluation → Analysis sequence for every target.

The built-in Liander 2024 dataset provides a ready-made benchmark covering five energy asset categories — MV feeders, station installations, transformers, solar parks, and wind parks — and is the fastest way to get a meaningful baseline comparison running:

.. code-block:: python

   from pathlib import Path
   from openstef_beam.benchmarking.benchmarks import create_liander2024_benchmark_runner
   from openstef_beam.benchmarking.storage.local import LocalBenchmarkStorage

   pipeline = create_liander2024_benchmark_runner(
       storage=LocalBenchmarkStorage(base_path=Path("./benchmark_results/MedianBaseline")),
   )

   pipeline.run(
       forecasters={"MedianBaseline": lambda target: MedianBaseline()},
       categories=["solar_park", "wind_park"],
   )

Results are written to the storage path in a structured layout: one subdirectory per target containing ``predictions.parquet``, evaluation scores, and HTML analysis plots.

Bringing Your Own Data
^^^^^^^^^^^^^^^^^^^^^^

When the Liander 2024 dataset does not match your use case, subclass ``SimpleTargetProvider`` and override the path resolution methods to point at your own parquet files:

.. code-block:: python

   from openstef_beam.benchmarking.target_provider import SimpleTargetProvider
   from openstef_beam.benchmarking.models.benchmark_target import BenchmarkTarget

   class MyGridTargetProvider(SimpleTargetProvider[BenchmarkTarget, list[str]]):
       measurements_path_template: str = "measurements/{name}.parquet"
       weather_path_template: str = "weather/{name}.parquet"

The ``{name}`` placeholder is substituted with each target's name at runtime. Once the provider is defined, pass it to ``BenchmarkPipeline`` alongside your evaluation and analysis configuration.

Comparing Multiple Runs
^^^^^^^^^^^^^^^^^^^^^^^

After running benchmarks for two or more model configurations, ``BenchmarkComparisonPipeline`` generates side-by-side comparison plots across all shared targets:

.. code-block:: python

   from openstef_beam.benchmarking.benchmark_comparison_pipeline import (
       BenchmarkComparisonPipeline,
   )
   from openstef_beam.benchmarking.storage.local import LocalBenchmarkStorage

   run_storages = {
       "MedianBaseline": LocalBenchmarkStorage(Path("./benchmark_results/MedianBaseline")),
       "GBLinear": LocalBenchmarkStorage(Path("./benchmark_results/GBLinear")),
   }

   comparison = BenchmarkComparisonPipeline(
       analysis_config=my_analysis_config,
       storage=LocalBenchmarkStorage(Path("./benchmark_results_comparison")),
       target_provider=my_target_provider,
   )
   comparison.run(run_data=run_storages)

The pipeline automatically detects which targets are present in all runs and restricts the comparison to that intersection, so partial benchmark runs do not cause failures.

Skipping Backtesting
^^^^^^^^^^^^^^^^^^^^

If you already have predictions from an external system or a previous run, BEAM can skip the backtesting phase entirely and run only evaluation and analysis. Place your forecast parquets in the expected layout (``backtest/<group_name>/<target_name>/predictions.parquet``) and point a ``BenchmarkPipeline`` at the existing storage. Each ``predictions.parquet`` must include an ``available_at`` column and one column per quantile named with the ``quantile_P<nn>`` convention.

.. note::

   The ``available_at`` column is what enables lead-time filtering during evaluation. Without it, BEAM cannot distinguish day-ahead from intraday predictions.


Dependency Summary
------------------

BEAM sits at the top of the OpenSTEF package hierarchy:

- ``openstef_core`` provides ``TimeSeriesDataset``, ``VersionedTimeSeriesDataset``, and ``BaseConfig`` — the data containers that flow through every BEAM phase.
- ``openstef_models`` provides the transform pipeline and model implementations that are wrapped by ``BacktestForecasterMixin`` adapters such as ``OpenSTEF4BacktestForecaster``.
- ``openstef_meta`` ensemble models (see :doc:`meta`) can be plugged into BEAM through the same ``BacktestForecasterMixin`` interface, enabling fair comparison against single-model baselines.

BEAM itself adds no new data structures that other packages depend on — it is a consumer, not a provider, which keeps the dependency graph acyclic.
