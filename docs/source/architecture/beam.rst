The OpenSTEF BEAM Package
=========================

The ``openstef_beam`` library — whose name expands to **Backtesting, Evaluation, Analysis,
and Metrics** — provides a rigorous, end-to-end framework for evaluating energy forecasting
models under realistic conditions. Where a simple train/test split can give misleading
confidence, BEAM replays historical data day by day, enforces strict temporal constraints,
and produces reproducible, comparable results across many energy assets and model types.

This page covers the internals of ``openstef_beam``: how its four phases connect, the
interfaces you implement to plug in a model, and how the benchmarking layer orchestrates
everything at scale. For the forecasting models themselves see :doc:`models`, and for the
core dataset primitives that BEAM builds on see :doc:`core`.

----

Why BEAM Exists
---------------

Standard cross-validation does not reflect how an energy forecasting model actually
operates. In production a model is retrained on a rolling basis and can only see data
that was available at the moment a forecast was issued. BEAM enforces this contract
through ``RestrictedHorizonVersionedTimeSeries``, a wrapper around
``openstef_core``'s ``VersionedTimeSeriesDataset`` that raises an error if any code
attempts to read data beyond the current simulation horizon. This single design decision
eliminates an entire class of evaluation bugs — data leakage — that would otherwise
inflate reported accuracy.

The four phases map directly onto the package's top-level sub-packages:

- ``openstef_beam.backtesting`` — simulate production forecasting over a historical window
- ``openstef_beam.evaluation`` — score predictions against ground truth with configurable metrics
- ``openstef_beam.analysis`` — generate per-target and lead-time visualisations
- ``openstef_beam.benchmarking`` — coordinate all three phases across many targets and models

----

The Backtesting Phase
---------------------

``BacktestPipeline`` is the engine of the backtesting phase. It drives two interleaved
schedules: a *prediction schedule* (how often forecasts are issued, defaulting to every
15 minutes) and a *retraining schedule* (how often the model is retrained on fresh data).
Both schedules are generated by ``BacktestEventGenerator``, which emits a stream of
``BacktestEvent`` objects — each event is either a ``FitEvent`` or a ``PredictEvent``.

The pipeline feeds each event to your forecaster through the ``BacktestForecasterMixin``
interface, which requires three things:

- a ``quantiles`` property listing the output quantiles (e.g. ``[0.05, 0.50, 0.95]``)
- a ``fit(data)`` method called on retraining events
- a ``predict(data)`` method called on prediction events, returning a ``TimeSeriesDataset``

Both ``fit`` and ``predict`` receive a ``RestrictedHorizonVersionedTimeSeries`` whose
``get_window()`` method accepts an ``available_before`` timestamp, ensuring the model
cannot accidentally use future revisions of the data.

Implementing a Custom Forecaster
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The minimal interface is straightforward. The example below implements a naïve baseline
that predicts the median of recent load history:

.. code-block:: python

    from datetime import timedelta
    from openstef_beam.backtesting.backtest_forecaster.mixins import (
        BacktestForecasterMixin,
    )
    from openstef_beam.backtesting.restricted_horizon_timeseries import (
        RestrictedHorizonVersionedTimeSeries,
    )
    from openstef_core.datasets import TimeSeriesDataset
    from openstef_core.types import Q


    class MedianBaselineForecaster(BacktestForecasterMixin):
        """Predict the median of the last 7 days as a flat forecast."""

        @property
        def quantiles(self) -> list[Q]:
            return [Q(0.05), Q(0.50), Q(0.95)]

        def fit(self, data: RestrictedHorizonVersionedTimeSeries) -> None:
            # Retrieve the last 7 days of data available at the current horizon
            window = data.get_window(
                start=data.horizon - timedelta(days=7),
                end=data.horizon,
                available_before=data.horizon,
            )
            self._median = float(window["load"].median())

        def predict(
            self, data: RestrictedHorizonVersionedTimeSeries
        ) -> TimeSeriesDataset | None:
            window = data.get_window(
                start=data.horizon,
                end=data.horizon + timedelta(hours=48),
            )
            index = window.index
            import pandas as pd

            df = pd.DataFrame(
                {
                    "load": self._median,
                    "quantile_P05": self._median * 0.8,
                    "quantile_P50": self._median,
                    "quantile_P95": self._median * 1.2,
                },
                index=index,
            )
            return TimeSeriesDataset(df)

.. note::

   The ``available_before`` argument to ``get_window()`` is the key guard against data
   leakage. Always pass ``data.horizon`` (or earlier) when retrieving training data inside
   ``fit()``. Omitting it in ``predict()`` is intentional — you are allowed to read the
   forecast horizon's feature data (e.g. weather forecasts) but not future load
   measurements.

Integrating OpenSTEF Models
----------------------------

If you are using a model from ``openstef_models``, BEAM ships a ready-made adapter so
you do not need to write the ``fit``/``predict`` boilerplate yourself.
``create_openstef4_preset_backtest_forecaster`` wraps any ``ForecastingWorkflowConfig``
into a ``ForecasterFactory`` — a callable that BEAM invokes once per benchmark target to
produce a fresh forecaster instance:

.. code-block:: python

    from openstef_beam.benchmarking.baselines.openstef4 import (
        create_openstef4_preset_backtest_forecaster,
    )
    from openstef_models.presets import ForecastingWorkflowConfig

    workflow_config = ForecastingWorkflowConfig(model_type="gblinear")

    forecaster_factory = create_openstef4_preset_backtest_forecaster(
        workflow_config=workflow_config,
        cache_dir="./model_cache",
    )

The factory pattern is important: because each target may be processed in a separate
process, BEAM needs to construct a clean forecaster per target rather than sharing state.

The Benchmarking Layer
-----------------------

``BenchmarkPipeline`` (in ``openstef_beam.benchmarking``) is the top-level orchestrator.
It ties together a *target provider*, one or more *forecaster factories*, and a
*storage backend*, then runs the full Backtesting → Evaluation → Analysis sequence for
every target in parallel.

The built-in ``create_liander2024_benchmark_runner()`` factory provides a ready-to-run
benchmark against the public Liander 2024 dataset (auto-downloaded from HuggingFace),
which is useful for validating a new model or reproducing published results:

.. code-block:: python

    import multiprocessing
    import os

    # Prevent thread contention when running multiple processes
    os.environ["OMP_NUM_THREADS"] = "1"
    os.environ["OPENBLAS_NUM_THREADS"] = "1"
    os.environ["MKL_NUM_THREADS"] = "1"

    from openstef_beam.benchmarking.benchmarks import create_liander2024_benchmark_runner
    from openstef_beam.benchmarking.baselines.openstef4 import (
        create_openstef4_preset_backtest_forecaster,
    )
    from openstef_models.presets import ForecastingWorkflowConfig

    runner = create_liander2024_benchmark_runner()

    runner.pipeline.run(
        forecaster_factories={
            "gblinear": create_openstef4_preset_backtest_forecaster(
                ForecastingWorkflowConfig(model_type="gblinear")
            ),
        },
        n_processes=multiprocessing.cpu_count(),
        output_path="./benchmark_results",
    )

Results are written to ``./benchmark_results/<model_name>/`` with one sub-directory per
target containing the raw prediction parquets, evaluation scores, and analysis plots.

Bringing Your Own Data
^^^^^^^^^^^^^^^^^^^^^^^

When the built-in datasets do not match your use case, subclass ``SimpleTargetProvider``
and override two methods that return paths to your measurement and weather parquet files.
The rest of the pipeline — event generation, evaluation, analysis — requires no changes.
See the ``examples/benchmarks/custom_benchmark/`` directory in the repository for a
complete worked example.

Evaluating Pre-existing Forecasts
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

If you already have predictions from an external system or a previous run, you can skip
backtesting entirely and point BEAM at a directory of parquet files. The expected layout
is::

    benchmark_results/MyForecasts/
    └── backtest/
        └── <group_name>/
            └── <target_name>/
                └── predictions.parquet

Each parquet must contain a ``DatetimeIndex`` named ``timestamp``, an ``available_at``
column recording when each forecast was generated, and one column per quantile named
using the ``Quantile(x).format()`` convention (e.g. ``quantile_P50``). BEAM uses
``available_at`` to reconstruct the lead-time dimension for analysis without re-running
any model code.

Multi-Run Comparison
---------------------

After running two or more models, ``BenchmarkComparisonPipeline`` produces side-by-side
comparison reports — global summaries, per-group breakdowns, and per-target detail pages
— as interactive HTML plots:

.. code-block:: python

    from openstef_beam.benchmarking.benchmark_comparison_pipeline import (
        BenchmarkComparisonPipeline,
    )
    from openstef_beam.benchmarking import LocalBenchmarkStorage

    run_data = {
        "gblinear": LocalBenchmarkStorage("./benchmark_results/gblinear"),
        "baseline": LocalBenchmarkStorage("./benchmark_results/MedianBaseline"),
    }

    comparison = BenchmarkComparisonPipeline()
    comparison.run(run_data=run_data, output_path="./benchmark_results_comparison")

``BenchmarkComparisonPipeline.run()`` automatically detects which targets are present in
all runs, so partial results from a run that was interrupted do not cause errors unless
you pass ``strict=True``.

Lead-Time Analysis
-------------------

One of BEAM's most operationally relevant outputs is the lead-time degradation curve:
how much does forecast skill drop as the prediction horizon extends from 1 hour to 48
hours? This matters because grid operators often need to know not just the average
accuracy but whether a model is still reliable at day-ahead horizons.

BEAM computes this automatically from the ``available_at`` column in the prediction
parquets. The analysis phase groups predictions by lead time, calculates the configured
metrics for each bucket, and renders the result as an interactive plot alongside the
per-target evaluation report. No additional configuration is needed — the lead-time
dimension is an inherent product of the backtesting simulation.

Package Dependencies
---------------------

``openstef_beam`` sits at the top of the OpenSTEF dependency graph:

- It consumes ``openstef_core`` for ``TimeSeriesDataset``, ``VersionedTimeSeriesDataset``,
  ``BaseConfig``, and shared type definitions. See :doc:`core` for details on these
  primitives.
- It consumes ``openstef_models`` through the ``baselines`` optional extra
  (``pip install openstef-beam[baselines]``), specifically the
  ``ForecastingWorkflowConfig`` and model presets. See :doc:`models` for the transforms
  and model architecture.
- It has no dependency on ``openstef_meta``. Ensemble models from that package can be
  wrapped in a ``BacktestForecasterMixin`` like any other model; see :doc:`meta` for
  details.

.. note::

   The ``baselines`` extra is optional by design. If you are only using BEAM to evaluate
   your own models or pre-existing forecasts, you do not need ``openstef_models``
   installed at all.
